# 负责人接续与内容维护

## 当前运行边界

本站当前为公开可访问的体验版本，2026-10-21 观察到访问策略 revision 2。本轮保留这一受众与原域名，未扩大权限；原私有首版记录保留为历史。页面继续设置 noindex/nofollow、robots 禁止爬取，这仅表达索引意愿，不是访问控制。

联系记录保存在本站数据库，负责人通过 `/inbox` 查看最近 100 条记录。负责人身份由 Sites 注入的登录信息和服务器端准入配置共同校验；登录站点不自动授予收件权限。平台身份与负责人配置均有效时，才允许读取、修改或删除。

负责人可保存「待处理 / 跟进中 / 已关闭」、下一动作与复看日期；跟进中必须填写下一动作。状态和日期只记录人工安排，不发送邮件、微信、自动提醒或合作确认。旧页面提交时若记录已被其他页面更新，服务端拒绝覆盖，需刷新核对。技术回执不代表人工阅读；处理状态本身也不代表已经联系客户。

## 一次受控验收

1. 打开 `/contact`，用明确标为“测试”的内容和示例联系方式填写四项必要资料。
2. 提交后记录 `YL-` 开头的回执。保存失败时应保留输入并显示失败信息。
3. 负责人使用自己的登录身份打开 `/inbox`，核对同一回执、内容和时间；刷新后记录仍应存在。
4. 同一次网络重试应返回同一回执。无身份或非负责人访问 `/api/inquiries` 应被拒绝。
5. 负责人为测试请求填写下一动作、跟进状态与复看日期，保存后刷新核对。另一个旧页面的修改应提示版本冲突。
6. 在确认测试记录可丢弃后执行页面内删除确认，刷新检查该回执不再出现。真实删除诉求须先核验提交者与请求。
7. 把浏览器、部署版本、观察到的结果记入任务。示例数据与真实客户数据分别标注，验收截图不含真实联系人。

系统级受控验证与负责人亲自使用分别记录。未完成真人登录/阅读时，不写“人工承接已验证”。

## 联系资料处理

收到真实问题后，由负责人判断是否适合讨论，再通过对方选择的联系方式联系。任何对外消息仍应由有授权的人确认和发送。本应用不自动承诺回复时间、预约日期、合作成立或经营结果。

需要更正或删除时，提交者可在联系入口注明回执与诉求。更正采用新提交补充，负责人核验后在下一动作中说明替代关系，原记录可按请求删除。删除按钮会在二次确认后删除该条请求的内容、联系方式和处理记录；网站没有恢复入口。不得为了测试删除真实请求。

当前没有自动删除计划、批量导出或自助撤回功能。保留周期与日常查阅节奏仍需由实际负责人确定，隐私页面如实说明此状态。建立定期清理计划后再同步更新实现与文字，不能只声明一个尚未执行的期限。现有列表只加载最新 100 条；量级超过这一范围前应补充分页与按回执查询，再继续扩大接收。

## 个人练习与联系资料的边界

`/practice` 的问题卡由用户主动保存到当前浏览器，一次保留一份。换设备、无痕窗口或清除网站数据后可能不可用；下载文件由浏览器本地生成。问题卡组件没有服务端保存、分析或联系提交；答案不放在 URL，也不自动带入联系表单。旧版本或损坏草稿在用户明确覆盖前保留，存储不可用时提示下载。网站负责人看不到读者的本机草稿。

## 内容维护

1. 按 [#38](https://github.com/moonstachain/yuanli-strategy-web/issues/38) 的范围修改页面源文件。方法定义以 Soul 正典为准，人物叙述以公开安全文脉为准。
2. 新增真实项目材料前核实发布范围；保留适用证据、观察日期和限制。不要把模拟样板或匿名改写当作已验证客户成果。
3. 在 PR 中列明改动页面、依据和验收；运行类型检查，涉及联系行为时运行测试，查看相关页面后构建。
4. GitHub 负责源码，Sites 发布镜像保持应用文件一致。发布时记录源码 SHA、版本 ID、部署状态与访问范围。

当前内容维护通过代码 PR 完成，未提供后台 CMS，也没有自动同步私人知识库。

## 发布与恢复

源分支用于审阅；现有主仓 `main` 的 GitHub Pages 工作流属于原媒体站。商业应用单独部署，不能把源代码合并和商业站公开当作同一个动作。

Sites 发布使用确切项目 ID、已推送的源码 SHA 和同一源码构建的归档；D1 迁移随版本执行。本轮只添加三个可空列，旧记录继续可读。检查版本/部署状态、十二条内容路由、分享资源与受控联系行为。

应用恢复使用 Sites 已保存的上一可用版本重新部署，并保留恢复时已确认的受众。数据库迁移不自动回滚；本轮新增列兼容旧版读取，回退应用不会恢复已删除的联系资料。每次发布后在 PR 中记录精确版本 ID 与部署结果，作为下一次恢复的依据。

## 仍需真人与运营验收

- 负责人亲自登录、查看测试请求并完成一次人工接续演练。
- 确定并实际执行保留期限与查阅节奏，演练更正/删除流程。
- 五名目标访客各自尝试定位、找问题、看判断、理解合作、提交需求；记录他们的真实理解与阻碍。
- 确认正式传播与索引准备程度后，再调整 robots、sitemap、正式域名与对外入口。

这些状态继续记录在 [#43](https://github.com/moonstachain/yuanli-strategy-web/issues/43) 与 [#44](https://github.com/moonstachain/yuanli-strategy-web/issues/44)。自动化通过不能替代真人理解、人工承接与商业结果。
