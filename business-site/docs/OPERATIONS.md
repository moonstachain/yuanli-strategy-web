# 负责人接续与内容维护

## 当前运行边界

首版为私密预览。接收记录保存在本站数据库，负责人通过 `/inbox` 查看；页面不发送邮件、微信或其他通知。负责人身份由 Sites 注入的登录信息和服务器端准入配置共同校验。登录站点不自动授予收件权限。

收件页目前展示最近 100 条记录与初始状态；尚无已读、跟进、关闭的写回界面。正式接收业务前，需明确日常查阅人、人工承接安排和状态记录位置，验收任务为 [#43](https://github.com/moonstachain/yuanli-strategy-web/issues/43)。不把技术回执当作人工处理记录。

## 一次受控验收

1. 打开 `/contact`，用明确标为“测试”的内容和示例联系方式填写四项必要资料。
2. 提交后记录 `YL-` 开头的回执。保存失败时应保留输入并显示失败信息。
3. 负责人使用自己的登录身份打开 `/inbox`，核对同一回执、内容和时间；刷新后记录仍应存在。
4. 同一次网络重试应返回同一回执。无身份或非负责人访问 `/api/inquiries` 应被拒绝。
5. 把浏览器、部署版本、观察到的结果记入任务。示例数据与真实客户数据分别标注，验收截图不含真实联系人。

系统级受控验证与负责人亲自使用分别记录。未完成真人登录/阅读时，不写“人工承接已验证”。

## 联系资料处理

收到真实问题后，由负责人判断是否适合讨论，再通过对方选择的联系方式联系。任何对外消息仍应由有授权的人确认和发送。本应用不自动承诺回复时间、预约日期、合作成立或经营结果。

需要更正或删除时，提交者可在联系入口注明回执与诉求；负责人核实后执行并记录。当前没有自动删除计划、批量导出或自助撤回功能。公开接收前需确定实际保留期限、处理负责人和可执行的删除流程，并同步更新隐私页面；不能只改文案而不建立处理能力。

## 内容维护

1. 按 [#38](https://github.com/moonstachain/yuanli-strategy-web/issues/38) 的范围修改页面源文件。方法定义以 Soul 正典为准，人物叙述以公开安全文脉为准。
2. 新增真实项目材料前核实发布范围；保留适用证据、观察日期和限制。不要把模拟样板或匿名改写当作已验证客户成果。
3. 在 PR 中列明改动页面、依据和验收；运行类型检查，涉及联系行为时运行测试，查看相关页面后构建。
4. GitHub 负责源码，Sites 发布镜像保持应用文件一致。发布时记录源码 SHA、版本 ID、部署状态与访问范围。

当前内容维护通过代码 PR 完成，未提供后台 CMS，也没有自动同步私人知识库。

## 发布与恢复

源分支用于审阅；现有主仓 `main` 的 GitHub Pages 工作流属于原媒体站。商业应用单独部署，不能把源代码合并和商业站公开当作同一个动作。

Sites 发布使用确切项目 ID、已推送的源码 SHA 和同一源码构建的归档；D1 迁移随版本执行。发布后检查版本/部署状态、九条内容路由、分享资源与一次受控联系保存。

应用版本恢复使用 Sites 已保存的上一可用版本重新私密部署。数据库迁移不因此自动回滚；更改数据结构前需要设计兼容性与数据恢复方案。首个版本尚无上一生产版本可回退时，应如实记录。

## 公开前仍需验收

- 负责人亲自登录、查看测试请求并完成一次人工接续演练。
- 明确保留期限、更正/删除处理与实际承接节奏。
- 五名目标访客各自尝试定位、找问题、看判断、理解合作、提交需求；记录他们的真实理解与阻碍。
- 确定公开受众和正式域名后，再调整访问策略、robots、sitemap、分享信息与对外入口。

这些条件属于执行任务的后续验收，不影响首版工程与私密预览交付；它们也不能由自动化通过替代。
